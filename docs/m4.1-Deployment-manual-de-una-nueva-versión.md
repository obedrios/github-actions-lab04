# Deployment manual de ua nueva version

Este es una guia autocontenida para insertar en **M4**, idealmente después de la validación inicial del deployment y antes del cierre del milestone.

Una vez que la primera versión de la aplicación está funcionando en ECS/Fargate, podemos practicar un segundo deployment manual.

Este ejercicio permite comprender qué sucede cuando modificamos el contenido de Docusaurus y queremos reflejar esos cambios en AWS.

El flujo será:

```
Modificar documentación
        │
        ▼
Construir nueva imagen
        │
        ▼
Publicar nueva versión en ECR
        │
        ▼
Registrar nueva revisión de Task Definition
        │
        ▼
Actualizar ECS Service
        │
        ▼
ECS reemplaza la Task anterior
        │
        ▼
Nueva versión en ejecución
```



### 1. Modificar el contenido de Docusaurus

Realizar un cambio visible en alguno de los documentos.

Por ejemplo:

```
docs/
└── m4-ecs-fargate.md
```

Agregar alguna modificación fácilmente identificable.

Ejemplo:

```
## Deployment version 2

Esta sección fue agregada para validar un nuevo deployment
de la aplicación en Amazon ECS.
```

Antes de continuar podemos comprobar localmente que Docusaurus sigue construyéndose:

```
npm run build
```

------

### 2. Definir un nuevo tag de imagen

El repositorio ECR fue configurado con:

```
IMMUTABLE
```

Por tanto, no debemos sobrescribir:

```
m3-v1
```

Para la nueva versión utilizaremos un nuevo tag:

```
export IMAGE_TAG="m3-v2"
```

Actualizar la URI:

```bash
export IMAGE_URI="${ECR_REPOSITORY_URI}:${IMAGE_TAG}"
```

Verificar:

```bash
echo "${IMAGE_URI}"
```

Conceptualmente:

```
Amazon ECR
    │
    ├── m3-v1
    │
    └── m4-v2
```

La primera imagen continúa disponible y puede utilizarse posteriormente para rollback.

------

### 3. Construir y publicar la nueva imagen

Utilizar el mismo patrón de M3 para generar un OCI Image Manifest single-platform:

```bash
docker buildx build \
  --platform linux/amd64 \
  --provenance=false \
  --sbom=false \
  --output type=image,push=true,oci-mediatypes=true \
  -t "${IMAGE_URI}" \
  .
```

Este comando realiza:

```
Source Code
    │
    ▼
Docker Build
    │
    ▼
OCI Image Manifest
    │
    ▼
Amazon ECR
    │
    ▼
m3-v2
```

Si se requiere credenciales temporales en Docker para poder publicar la imagen, entonces, 

```bash
aws ecr get-login-password \
  --profile aws-lab \
  --region "${AWS_REGION}" \
  | docker login \
      --username AWS \
      --password-stdin "${ECR_REGISTRY}"
```



### 4. Verificar la nueva imagen en ECR

Ejecutar:

```bash
aws ecr describe-images \
  --profile aws-lab \
  --repository-name "${ECR_REPOSITORY}" \
  --image-ids imageTag="${IMAGE_TAG}" \
  --region "${AWS_REGION}" \
  --query 'imageDetails[0].[imageTags,imageDigest,imageManifestMediaType,imagePushedAt]' \
  --output table
```

Esperamos encontrar:

```markdown
-----------------------------------------------------------------------------
|                              DescribeImages                               |
+---------------------------------------------------------------------------+
|  m3-v2                                                                    |
|  sha256:5ddf91384ce396d5b28e94ad71bbe4bce9af2af026282db45197e39d8dc897d9  |
|  application/vnd.oci.image.manifest.v1+json                               |
|  2026-10-10T18:02:48.924000-07:00                                         |
+---------------------------------------------------------------------------+
```

Registrar el nuevo digest:

```bash
export NEW_IMAGE_DIGEST=$(aws ecr describe-images \
  --profile aws-lab \
  --repository-name "${ECR_REPOSITORY}" \
  --image-ids imageTag="${IMAGE_TAG}" \
  --region "${AWS_REGION}" \
  --query 'imageDetails[0].imageDigest' \
  --output text)
```

Verificar:

```bash
echo "${NEW_IMAGE_DIGEST}"
```

------

### 5. Actualizar la Task Definition

La Task Definition anterior apunta a:

```bash
lab04-docusaurus:m3-v1
```

Para desplegar la nueva imagen debemos crear una **nueva revisión**.

Modificar:

```bash
task-definition.json
```

y actualizar únicamente el campo:

```json
"image": "<ECR_REPOSITORY_URI>:m4-v2"
```

Por ejemplo:

```JSON
{
  "name": "lab04-docusaurus",
  "image": "123456789012.dkr.ecr.us-east-1.amazonaws.com/lab04-docusaurus:m4-v2",
  "essential": true,
  "portMappings": [
    {
      "containerPort": 80,
      "protocol": "tcp"
    }
  ]
}
```

No debemos modificar la revisión anterior.

ECS mantiene versiones sucesivas de una Task Definition.

Conceptualmente:

```
lab04-docusaurus:1
        │
        └── m3-v1

lab04-docusaurus:2
        │
        └── m4-v2
```

------

### 6. Registrar una nueva revisión

Ejecutar:

```bash
aws ecs register-task-definition \
  --profile aws-lab \
  --cli-input-json file://task-definition.json \
  --region "${AWS_REGION}"
```

Consultar la revisión más reciente:

```bash
aws ecs describe-task-definition \
  --profile aws-lab \
  --task-definition "${TASK_FAMILY}" \
  --region "${AWS_REGION}" \
  --query 'taskDefinition.[family,revision,containerDefinitions[0].image]' \
  --output table
```

Esperamos algo similar a:

```markdown+
-------------------------------------------------------------------------
|                        DescribeTaskDefinition                         |
+-----------------------------------------------------------------------+
|  lab04-docusaurus                                                     |
|  2                                                                    |
|  565866186032.dkr.ecr.us-east-1.amazonaws.com/lab04-docusaurus:m3-v2  |
+-----------------------------------------------------------------------+
```

Obtener la revisión:

```bash
export TASK_REVISION=$(aws ecs describe-task-definition \
  --profile aws-lab \
  --task-definition "${TASK_FAMILY}" \
  --region "${AWS_REGION}" \
  --query 'taskDefinition.revision' \
  --output text)
```

Verificar:

```bash
echo "${TASK_REVISION}"
```

------

### 7. Actualizar el ECS Service

Actualizar el servicio para utilizar la nueva revisión:

```bash
aws ecs update-service \
  --profile aws-lab \
  --cluster "${ECS_CLUSTER}" \
  --service "${ECS_SERVICE}" \
  --task-definition "${TASK_FAMILY}:${TASK_REVISION}" \
  --region "${AWS_REGION}"
```

Conceptualmente:

```
ECS Service
    │
    │ Old:
    │ Task Definition :1
    │ m3-v1
    │
    ▼
Deployment
    │
    ▼
ECS Service
    │
    │ New:
    │ Task Definition :2
    │ m4-v2
```

ECS comenzará a reemplazar la Task anterior por una nueva.

------

### 8. Esperar estabilidad

Ejecutar:

```bash
aws ecs wait services-stable \
  --profile aws-lab \
  --cluster "${ECS_CLUSTER}" \
  --services "${ECS_SERVICE}" \
  --region "${AWS_REGION}"
```

Este comando normalmente no imprime salida cuando termina correctamente.

Podemos verificar el código de retorno:

```
echo $?
```

Resultado esperado:

```
0
```

Después consultar:

```bash
aws ecs describe-services \
  --profile aws-lab \
  --cluster "${ECS_CLUSTER}" \
  --services "${ECS_SERVICE}" \
  --region "${AWS_REGION}" \
  --query 'services[0].[status,desiredCount,runningCount,pendingCount,taskDefinition]' \
  --output table
```

Esperamos:

```markdown
---------------------------------------------------------------------------
|                            DescribeServices                             |
+-------------------------------------------------------------------------+
|  ACTIVE                                                                 |
|  1                                                                      |
|  1                                                                      |
|  0                                                                      |
|  arn:aws:ecs:us-east-1:565866186032:task-definition/lab04-docusaurus:2  |
+-------------------------------------------------------------------------+
```

### 9. Obtener la nueva Task

Ejecutar:

```bash
export TASK_ARN=$(aws ecs list-tasks \
  --profile aws-lab \
  --cluster "${ECS_CLUSTER}" \
  --service-name "${ECS_SERVICE}" \
  --desired-status RUNNING \
  --region "${AWS_REGION}" \
  --query 'taskArns[0]' \
  --output text)
```

Verificar:

```bash
echo "${TASK_ARN}"
```

```bash
aws ecs describe-tasks \
```

### 11. Comparar el digest

Obtener el digest ejecutado:

```bash
export RUNNING_IMAGE_DIGEST=$(aws ecs describe-tasks \
  --profile aws-lab \
  --cluster "${ECS_CLUSTER}" \
  --tasks "${TASK_ARN}" \
  --region "${AWS_REGION}" \
  --query 'tasks[0].containers[0].imageDigest' \
  --output text)
```

Comparar:

```bash
if [ "${NEW_IMAGE_DIGEST}" = "${RUNNING_IMAGE_DIGEST}" ]; then
  echo "PASS: ECS is running the new image"
else
  echo "FAIL: Running image digest does not match ECR"
fi
```

Resultado esperado:

```
PASS: ECS is running the new image
```

------

### 12. Obtener la nueva Public IP

La nueva Fargate Task puede tener una nueva ENI y una nueva Public IP.

Obtener la ENI:

```bash
export ENI_ID=$(aws ecs describe-tasks \
  --profile aws-lab \
  --cluster "${ECS_CLUSTER}" \
  --tasks "${TASK_ARN}" \
  --region "${AWS_REGION}" \
  --query "tasks[0].attachments[0].details[?name=='networkInterfaceId'].value | [0]" \
  --output text)
```

Obtener Public IP:

```bash
export PUBLIC_IP=$(aws ec2 describe-network-interfaces \
  --profile aws-lab \
  --network-interface-ids "${ENI_ID}" \
  --region "${AWS_REGION}" \
  --query 'NetworkInterfaces[0].Association.PublicIp' \
  --output text)
```

Verificar:

```bash
echo "${PUBLIC_IP}"
```

Ejecutar:

```bash
curl -I "http://${PUBLIC_IP}"
```

Esperamos:

### 15. Qué ocurrió durante el deployment

El proceso completo fue:

```
Source v1
   │
   ▼
m3-v1
   │
   ▼
Task Definition :1
   │
   ▼
Fargate Task A
```

Después:

```
Source v2
   │
   ▼
m4-v2
   │
   ▼
Task Definition :2
   │
   ▼
Fargate Task B
```

ECS realizó la transición:

```
Task A
m3-v1
   │
   ▼
Deployment
   │
   ▼
Task B
m4-v2
```

### 18. Aprendizaje principal

Modificar el código fuente no actualiza automáticamente una aplicación ejecutándose en ECS.

El flujo necesario es:

```
Source Change
     │
     ▼
New Container Image
     │
     ▼
Amazon ECR
     │
     ▼
New Task Definition Revision
     │
     ▼
ECS Service Update
     │
     ▼
New Fargate Task
```

Esto demuestra una separación importante:

```
Source Code
    ≠
Container Image
    ≠
Task Definition
    ≠
Running Task
```

Cada etapa produce o referencia un artefacto distinto.

### 19. Relación con M6 y M7

Este proceso manual será la base de:

```
M6 — GitHub Actions + OIDC
```

donde automatizaremos:

```
git push
   │
   ▼
docker build
   │
   ▼
ECR push
   │
   ▼
Task Definition revision
   │
   ▼
ECS update-service
```

También prepara:

```
M7 — Rollback
```

porque ahora conservamos:

```
Task Definition :1 → m3-v1
Task Definition :2 → m4-v2
```

y podemos regresar explícitamente a una revisión estable si una nueva versión presenta problemas.

Esta sección además mejora bastante M4 porque ya no solo demuestra el **primer deployment**, sino también el ciclo operativo real de **“cambio → nueva imagen → nueva revisión → nuevo deployment”**, que es justo lo que después automatizaremos en M6.
